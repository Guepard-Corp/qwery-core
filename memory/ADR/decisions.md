# Decisions — Session 2026-05-22

Project: AI data agent, connects to datasources, TUI experience as a priority.

| # | Topic | Decision | Rationale |
|---|-------|----------|-----------|
| 1 | TUI framework | **Ink** (TypeScript) | React for the terminal, mature ecosystem, used by Claude Code / Gemini CLI |
| 2 | Architecture | **Extension-based core** | Lean core + pluggable extensions for datasources. Keeps the agent minimal, allows third-party connectors |
| 3 | Extension distribution | **npm registry as marketplace** | No custom registry; in-TUI search command lets the user (and the agent itself) discover and install extensions |
| 4 | Bundled defaults | **File-format readers only** (CSV, JSON, SQLite) | Zero-/low-dependency formats stay in core for cold-start UX. All server datasources (MySQL, Postgres, etc.) and heavier formats (Parquet) are extensions |
| 5 | MCP support | **First-class, native** | MCP servers are action/tool integrations (Notion, Slack, GitHub). Extensions are data-source connectors that expose a schema for the LLM to reason over. The two compose (e.g. extension reads Parquet, MCP Notion drafts report) |
| 6 | SDK | **`@qwery/extension-sdk` kept stable**, lives in the qwery-agent monorepo alongside first-party extensions | qwery-agent is a greenfield project (qwery-core is reference/inspiration only). Mono-repo guarantees first-party extensions break first if the SDK changes — forces disciplined versioning |
| 7 | Compute engine | **DuckDB embedded in core** | DuckDB-first architecture: backs Query, Sample, Profile, Transform, and unifies file-format readers (CSV/JSON/SQLite via `read_*_auto`). Other compute engines (Polars, DataFusion, etc.) only as extensions for niche use cases |
| 8 | Core agent tools | **`Bash`, `Read`, `Write`, `Query`, `Schema`, `Sample`, `Profile`, `Transform`** | Data-engineer / data-scientist primitives. `Sample` and `Profile` are distinct tools (not buried in Query) to guide the LLM toward safe defaults. `Transform` is the in-DuckDB compute step distinct from `Query` against a connected source. `Bash` kept as universal escape hatch (run scripts, generate visualizations, ad-hoc orchestration); security mitigations to be designed at implementation time |
| 9 | Distribution | **Install script + Bun-compiled binaries (primary)**, npm secondary, brew later (community) | `curl …\|sh` detects platform and pulls the right Bun-compiled binary from GitHub Releases. Zero-dep install, fast startup. `npm i -g qwery` kept as a secondary channel for users who already have Node. brew formula deferred to community |
| 10 | Versioning | **Independent versioning + Changesets** | `@qwery/extension-sdk` must stay ultra-stable (decision #6); lockstep would force needless major bumps on the SDK each release. Each monorepo package versioned independently, releases driven by Changesets |
| 11 | GFS integration | **GFS bundled as hard dependency**, MySQL/Postgres extensions route all queries through `gfs query`, auto-selective branching on destructive ops, graceful fallback for non-GFS datasources | GFS ([Guepard-Corp/gfs](https://github.com/Guepard-Corp/gfs)) is "git for data": branching + time-travel + commits. It is the safety net that lets the AI agent experiment on production data without fear. Bundled at install time (qwery install script chains into the GFS installer). Currently covers PostgreSQL 13-18 and MySQL 8.0-8.1. For unsupported datasources (SQLite, CSV, BigQuery, etc.) the agent must warn + require explicit confirmation before destructive writes. Auto-branching scope: DROP / DELETE / TRUNCATE / UPDATE without WHERE / schema changes (best-effort detection) |
| 12 | Architecture style + enforcement | **Hexagonal (ports & adapters)** enforced by **`dependency-cruiser`** in CI | Multiple adapters per port are real here (multi-LLM, multi-datasource via extensions, optional GFS, TUI today / web later). Avoid over-abstracting single-adapter ports. dependency-cruiser ships declarative rules, CI-friendly, produces dependency graphs usable as documentation |
| 13 | Runtime | **Bun** | Aligns with decision #9 (Bun-compiled binaries for distribution). Native TS, fast startup, single-binary builds, good fit for a CLI |
| 14 | Build tool (monorepo) | **Turborepo** | Standard for TS monorepos, cache-aware, integrates cleanly with `bun x turbo` and Changesets |
| 15 | Test framework | **`bun test`** | Avoids a second runner: Bun is already the runtime. ~10× faster than Vitest, Vitest-compatible API. Fall back to Vitest only if a hard limit appears |
| 16 | Test coverage (non-negotiable) | Tiered thresholds enforced in CI via `bun test --coverage`: **domain 100% / application ≥90% / adapters ≥70% / extensions ≥80% / cli (Ink) ≥50% + snapshot tests** | Pure domain logic has no excuse for missing coverage. Adapters and UI carry harder-to-mock paths, so thresholds relax. First-party extensions act as references for third parties — they must be exemplary |
| 17 | LLM abstraction | **Vercel AI SDK** (`ai`) | Provider-agnostic API (Anthropic, OpenAI, Bedrock, Google, Mistral, …). Streaming, tool-use, structured output supported. Plugs naturally into the `LLMProvider` port |
| 18 | Bash sandboxing | **Filesystem + process scopes only** (no network sandbox by default). macOS Seatbelt (`sandbox-exec`), Linux bubblewrap or landlock. Windows deferred | (a) FS: Bash can only write inside the workspace and `~/.qwery/cache`. (c) Process: no `kill`, no daemonization. Network left open (otherwise breaks `pip`/`apt`/`curl` workflows). Network sandbox can be opt-in later |
| 19 | User config | **`~/.qwery/` (global) + `.qwery/` (per-project)**, both directories. Project overrides global (merge keys, project wins on conflict). Secrets via **OS Keychain** with automatic fallback to `~/.qwery/credentials.enc` (encrypted, master-key derived from passphrase or `QWERY_MASTER_KEY` env var) | Directories (not files) let us split `config.json`, `connections.json`, cache, and GFS branch metadata. Keychain detection done via canary write at startup using `@napi-rs/keyring`; falls back transparently on headless Linux / CI / WSL where libsecret is absent |
| 20 | Monorepo layout | **Explicit hexagonal layout** | `apps/cli/` (Ink TUI = primary adapter), `packages/domain/`, `packages/application/`, `packages/adapters/{llm-aisdk, compute-duckdb, branching-gfs, ui-ink}`, `packages/extension-sdk/`, `packages/extensions/{mysql, postgres, sqlite, csv, json}`, `tooling/` (turbo, dep-cruiser, scripts), `.changeset/`. One adapter = one package (independent versioning + isolation) |
| 21 | LLM provider tiers | **Tier 1 — `qwery-model` cloud** (free + throttled, login lifts the throttle, in development). **Tier 2 — `qwery-model` local** (downloaded model run via Ollama). **Tier 3 — BYOK** via Vercel AI SDK: **OpenAI, Anthropic, Ollama, Bedrock, Azure**. Ollama plays a dual role: runtime for the local tier, and BYOK target for users with their own model setup. Credentials in OS Keychain per decision #19 | Cloud-first default gives an out-of-the-box experience; local + BYOK preserve privacy and offline use. First-run wizard must surface the privacy implications of cloud default explicitly |
| 22 | Telemetry & observability | **Telemetry ON by default** via PostHog, **strict allowlist** of events (version, OS, command name without args, duration, error codes). **Never** captured: query content, table/column names, connection strings, results, prompts. First-run banner discloses + offers `qwery telemetry off` / `QWERY_TELEMETRY=0`. **Sentry** for crash reports with aggressive sanitization (`beforeSend` scrubs paths, SQL strings, credentials from stack traces). What is sent is fully documented in a public reference | Out-of-the-box visibility for product decisions while staying defensible vs GDPR and OSS community trust. Transparency > stealth |
| 23 | Release pipeline | **GitHub Actions + Changesets** | Changesets PR-bot creates "Version Packages" PRs; merge triggers npm publish + Bun cross-compile (darwin/linux/windows × x64/arm64) + GitHub Release with binaries. Install script (`get.qwery.dev`) pulls from GitHub Releases |
| 24 | License | **MIT** | Permissive, standard for OSS CLIs and SDKs. No copyleft friction for third-party extensions or enterprise adoption |
| 25 | Error model | **Coded errors** (`E0001`, …) with stable codes referencing a public docs URL. The agent itself is **auto-corrective** within bounded retry budgets (limits to define in a later milestone) | Stable error codes give the agent a precise signal for retry/skip/escalate decisions; doc links give the human user a path forward. Auto-correction limits left open for now to avoid premature commitment |
| 26 | Artifact domain model | **`Artifact` as base abstraction**, modeled as a Zod **discriminated union** by `type`. MVP ships **`QueryArtifact`** only. Other variants (`ReportArtifact`, `QuerybookArtifact`, `ApiArtifact`, `AppArtifact`, …) will be contributed **via the extension SDK** — third parties can register new variants, their repository, their UI tab, and their associated tools | Treats analytical outputs (queries, reports, notebooks, apps) as first-class reusable assets, not transient tool-call side effects. Discriminated union keeps TypeScript narrowing clean and the schema future-proof. Pushing non-MVP variants to extensions matches decisions #2 / #6 and lets the community contribute new artifact kinds without core changes |
| 27 | Storage scope split | **User-scoped** (`~/.qwery/storage/`): conversations, messages, datasources, credentials, preferences. **Project-scoped** (`./.qwery/storage/`): artifacts only. `./.qwery/` is **auto-initialized at first launch** in the working directory with a one-line log; user can `.gitignore` or commit it | Clean uninstall story: removing qwery and wiping `~/.qwery/` leaves no user-level traces. Artifacts (saved queries today, reports/querybooks tomorrow) are project deliverables — they belong with the project, can travel via git, and don't pollute the global namespace. Auto-init keeps the UX frictionless |
| 28 | Privacy boundary by tool design | **The LLM never receives row-level data.** Four data tools enforce the boundary: **`schema(target)`** describes an input table/file (columns + types, no rows). **`runQuery(sql)`** accepts only AGGREGATE-ONLY SQL (every projected column is an aggregate function, exactly 1 row of output; validated locally by an SQL-clause parser); returns the scalar to the LLM. **`describeQuery(sql)`** returns the output column list via DuckDB `PREPARE` (no execution, no rows). **`present(sql, template)`** executes a query and renders it locally via a Mustache template with helpers (`money`, `int`, `pct`, `date`, `{{#rows}}…{{/rows}}`); the LLM only sees `{ ok, rowCount }`, the user sees the rendered output | Differentiates qwery-agent from coding agents and from qwery-core/qwery-enterprise (which only minimize data for chart generation). Production data values never enter LLM context — eliminates a major class of leaks (prompt-leak surfaces, model-training contamination, third-party API exposure). The trade-off: the agent can't narrate values it never saw; it generates templates, the local renderer fills them. Aggregates remain narratable (scalar facts the user asked for). |
| 29 | Quality gates (git hooks) | **`simple-git-hooks`** runs **pre-commit** (fast, only changed files): Biome lint+format, `tsc --noEmit` on changed files, `dependency-cruiser`, secret scan (gitleaks if installed), commit-msg via **commitlint** (Conventional Commits). **pre-push** (thorough, all files): full typecheck, `bun test --coverage` with tiered thresholds (decision #16), build, bundle size budget, `bun pm audit`, **privacy invariant test** (decision #31). Hooks emit structured error output; a fix loop with an LLM may be wired later — for MVP, failures just block the action with readable messages | Cheap, deterministic floor on code quality. pre-commit must stay under ~5 s or contributors will bypass it; pre-push is allowed to take longer (~60 s) since it runs less often. Splitting the two prevents bypassing |
| 30 | Lint + format + commit conventions | **Biome** (single tool, Rust, replaces ESLint + Prettier) with a project-level `biome.json`. **commitlint** with `@commitlint/config-conventional` validates each commit message; Changesets (decision #10) reads the convention to compute semver bumps | Biome is ~10× faster than ESLint+Prettier, single config, no plugin sprawl. Conventional Commits give predictable changelogs and bump computation. |
| 31 | Privacy invariant test | A dedicated test harness (`tooling/privacy-check.ts`) wraps the LLM provider with a recording shim, runs the agent loop against `data/sales.csv` with prompts that span all four tools, and **asserts that no row-level value from the CSV appears in any payload sent upstream**. Runs in pre-push and on every PR | Decision #28 is the product's hardest commitment. Without an automated guard, a single careless tool refactor could silently leak production data into prompts. A failing invariant blocks release |
| 32 | Documentation conventions | **`AGENTS.md`** at the repo root is the entry point for AI contributors: strict rules on code quality, layout, hexagonal layers, privacy invariants, with forwards to `memory/ADR/` for decisions and **`memory/diagrams/`** for Mermaid architecture diagrams (`architecture.md`, `agent-loop.md`, `privacy-boundary.md`, `package-deps.md`). README.md stays human-oriented; AGENTS.md is the machine-oriented contract | AI contributors and humans both need a single, authoritative pointer. Separating AGENTS.md (rules) from README.md (onboarding) avoids the "everything in one file" rot |
| 33 | Use cases live in application, not domain | **Use cases live exclusively in `packages/application/use-cases/<aggregate>/<operation>.ts`**, never in `domain`. One use case = one file = one class OR one function (no interface-vs-implementation split, no `Service`/`Handler`/`UseCase` suffix). Use cases depend on **ports from domain**, never on concrete adapters. The composition root in `apps/cli/src/main.tsx` injects real adapters | Strict Hex/Clean Architecture alignment: domain stays pure (entities, value objects, ports). Application owns orchestration. dep-cruiser already enforces that domain imports nothing else in the repo; this decision lifts the discipline to the human/agent layer too. Diverges from qwery-core's `domain/{usecases,services}` split because that split has zero ROI for single-implementation use cases (no library boundary, no multi-impl polymorphism) |
| 34 | Persistent unit is `Session`, not `Conversation` | The persistent dialogue entity is named **`Session`** (`packages/domain/src/entities/session.entity.ts`). Messages reference it via `sessionId`. The resume command is **`/resume`** (ADR U7 updated). The chat *tab* keeps its name "Chat" — the user "chats" within a "session" | Diverges from qwery-core (which uses `Conversation`). For a TUI tool, "session" is the natural lifecycle vocabulary (cf. `tmux session`, `psql session`); `Conversation` is web-product vocabulary. Reserving "conversation" as a potential sub-concept of a session (branching threads, sub-agent dialogues) keeps future options open. `/resume` is verb-first, clearer than entity-first `/session` |
| 35 | Persistence backend | **SQLite via `bun:sqlite`**, exposed as a new adapter `@qwery/adapter-persistence-sqlite` implementing the existing repository ports (`ISessionRepository`, `IMessageRepository`, `IUsageRepository`, `IDatasourceRepository`). It **replaces the JSON-file adapter** and is now the only persistence adapter. The JSON-file adapter (`@qwery/adapter-persistence-file`) was used once to migrate existing `~/.qwery/storage` data into the DB, then **deleted**; its `ISecretVault` was relocated to the CLI composition root (`apps/cli/src/infra/secret-vault.ts`). Complex fields (`Session.datasources`, `Message.content`/`metadata`, `Datasource.config`) are stored as JSON columns; flat fields (usage token/cost counters, timestamps, slugs) are promoted to real columns + indexes. The `ISecretVault` is **injected** into `createSqlitePersistence` (not constructed inside it), so the sqlite adapter depends on no other adapter (honors the `adapters-must-not-cross-import` rule, ADR #12); the composition root builds the file-backed vault (`apps/cli/src/infra/secret-vault.ts`) and injects it. Migration was a one-shot copy of file-storage rows into the DB, run from the CLI (the only layer that could import both adapters) while both still existed; the JSON files under `~/.qwery/storage` are left untouched as a backup, and the migrator + file adapter were then removed. Secret handles (`enc:v1:…`) were copied verbatim and stay decryptable because the same master key (`~/.qwery/.master.key`) is reused |
| 36 | App packaging & install | **`bun build --compile` single-file executable + sidecar `libduckdb` + bash wrapper**, shipped as a per-platform tarball `qwery-<os>-<arch>.tar.gz` (layout: `bin/qwery` wrapper, `lib/qwery-bin`, `lib/libduckdb.{dylib,so}`) and installed under `~/.qwery` by a `curl \| bash` script at the repo root (`install`, modeled on the GFS installer). Targets: **macos-aarch64, macos-x86_64, linux-x86_64, linux-aarch64** (Windows deferred). Each platform's tarball is built on its own native CI runner via `scripts/build-release.ts` (`bun run build:release`); cross-compilation is not attempted. During compile, every `@duckdb/node-bindings-<platform>/duckdb.node` **except the host's** is marked `--external` (plus `react-devtools-core`), so the bundler stops resolving uninstalled platforms while the host addon stays embedded. The installer detects os/arch (normalizing `arm64→aarch64`, Rosetta→aarch64), downloads from `github.com/Guepard-Corp/qwery-agent/releases`, verifies the gzip, lays out `~/.qwery/bin` + `~/.qwery/lib`, writes `~/.qwery/version` for upgrade short-circuiting, and adds `~/.qwery/bin` to `$PATH`. `--archive <path>` installs a local tarball (CI/testing); `--version`, `--no-modify-path` mirror GFS | **Amends ADR #9's "Bun-compiled binaries" premise**: a *pure* single binary is impossible because `@duckdb/node-api`'s native addon `dlopen()`s `@rpath/libduckdb.{dylib,so}`, a companion shared library `bun --compile` does not embed (verified: the embedded `duckdb.node` extracts to a temp dir and fails with `Library not loaded: @rpath/libduckdb.dylib`). Shipping the engine as a sidecar and exporting `DYLD_LIBRARY_PATH`/`LD_LIBRARY_PATH` from a thin wrapper resolves it (validated end-to-end: a compiled probe ran `SELECT version()` from outside the repo). This still delivers the GFS UX — one `qwery` on `$PATH` from a `curl \| bash` — and the tarball model matches GFS (which ships a single static Rust binary; ours ships a binary + engine). Per-platform native runners sidestep cross-compiling the addon. Tarball is ~55 MB compressed (~165 MB on disk), dominated by `libduckdb`; acceptable for a data tool, optimizable later | The JSON-file adapter's access patterns degrade and risk corruption: `findAll()` walks and parses every file across all sessions (called at startup for history), `findById()` linear-scans the whole tree, and the read/write lock in `lock.ts` is **in-memory and single-process only** — two `qwery` instances on the same `~/.qwery/storage` can tear writes. SQLite gives indexed lookups, in-engine sort/filter/aggregation (usage totals, ordered session lists), cross-process locking (WAL + `busy_timeout`), and ACID transactions, eliminating the hand-rolled locking and the no-transaction inconsistency window. Cost is near-zero here: Bun ships `bun:sqlite` built-in (no native install; DuckDB already establishes an embedded engine is acceptable), and the hexagonal ports make this a contained adapter swap, not a rewrite. SQLite (OLTP) is the right tool for frequent small metadata writes — distinct from DuckDB (OLAP), which stays dedicated to the privacy-boundary analytical pipeline (ADR #28); the two engines keep clean, separate roles. Known tradeoff: the vault crypto still lives in the file adapter, so a future shared/extracted vault package may be warranted; for now injection avoids duplication and the cross-import rule |
| 37 | App auto-update | **Unified "stage-in-background, apply-at-next-startup" model for both `qwery` and the bundled `gfs` — no live hot-swap.** Two responsibilities, cleanly split: **(1) Apply (in the bash wrapper `bin/qwery`, ADR #36, before it `exec`s the binary).** On launch the wrapper checks `~/.qwery/staged/`; for each verified staged artifact it performs an **atomic swap** — `qwery`: `mv lib lib.old && mv staged/qwery-<v>/lib lib`; `gfs`: `mv` the new binary over `~/.qwery/bin/gfs` (or wherever the bundled gfs lives) — keeping the previous copy as `*.old` for one-step rollback, then clears the applied staging dir. The binary itself is never replaced while running; the wrapper is the only pre-boot hook and the only safe place to touch it. **(2) Detect + download (in-app, non-blocking `UpdateChecker` service, off the render path).** On startup and on a low-frequency ticker it queries the release sources — qwery: `api.github.com/repos/Guepard-Corp/qwery-agent/releases/latest`; gfs: its GitHub releases / `gfs.guepard.run` — compares to the **currently-running version** (prerequisite: the binary learns its own version, by reading `~/.qwery/version` next to the install or baking it at compile in `scripts/build-release.ts`) and, if newer **and not already staged**, downloads the per-platform tarball **plus its checksum** into `~/.qwery/staged/<artifact>-<version>/`, verifies (gzip + checksum), and leaves it for the wrapper. Idempotent ("download if not already done"): a present+verified staging dir is skipped; a partial/interrupted download is incomplete and re-fetched. A discreet status-bar hint ("update ready — restart to apply") is the only UX; nothing is applied mid-session. Opt-out via `QWERY_NO_UPDATE_CHECK`. gfs and qwery stage/apply **independently** (ADR #10) | A running `bun --compile` binary **cannot hot-swap its own code** — the process holds the old image in memory until it re-execs, so any qwery update is necessarily "apply on next start". gfs *could* be swapped live (it is a fresh `execFile` child per command, via `spawnRunner` in `@qwery/adapter-branching-gfs`), but unifying both artifacts on the **same stage-then-apply-at-startup** model deletes a whole class of complexity (no in-flight-command lock, no mid-command race, no coordination) for one consistent, **crash-safe** path: the atomic `rename` swap means an interrupted update never leaves a half-written binary, and `*.old` is a free rollback. The wrapper already exists as the pre-boot indirection (ADR #36) and is the natural home for "apply". The app stays simple — it only *detects and downloads to staging*, never mutates live binaries. Reuses ADR #23 release artifacts and the installer's `~/.qwery/version` short-circuit idea. Accepted trade-off: updates land on next launch, not instantly — fine for a CLI, and it sidesteps interrupting an active session; no user consent prompt needed since nothing is replaced under a live process. Security: tarball + checksum from the official repo only, **never** `curl \| bash` spawned from the running app (supply-chain surface) |
